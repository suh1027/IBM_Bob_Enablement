# Company Development Standards

이 문서는 본 프로젝트에서 IBM Bob을 사용하여 개발할 때 따라야 하는
기업 내부 공통 개발 기준을 정의합니다.

## 1. 기존 코드 우선 확인

- 코드를 수정하기 전에 현재 프로젝트 구조와 기존 구현을 먼저 확인한다.
- 기존 코드로 해결 가능한 경우 불필요하게 새로운 구조를 추가하지 않는다.
- 기존 기능과 데이터를 가능한 한 유지한다.

## 2. 변경 범위 관리

- 사용자가 요청한 작업과 직접 관련된 영역만 수정한다.
- 관계없는 코드나 파일은 임의로 변경하지 않는다.
- 대규모 리팩터링은 별도 요청이 없는 경우 수행하지 않는다.
- 기존 파일을 삭제하거나 프로젝트 구조를 크게 변경해야 하는 경우 먼저 사용자에게 알린다.

## 3. Dependency 관리

- 새로운 Framework, Library, Package를 임의로 추가하지 않는다.
- 새로운 Dependency가 필요한 경우 추가하기 전에 사용자에게 이유와 영향을 설명한다.
- 기존 Dependency 또는 현재 기술 구조로 해결할 수 있는 방법을 우선한다.

## 4. Security

- Password, API Key, Access Token, Secret 등의 민감정보를 코드에 직접 작성하지 않는다.
- 기존 인증, 권한, 보안 관련 설정을 임의로 제거하거나 완화하지 않는다.
- 외부 시스템으로 프로젝트 정보를 전달해야 하는 경우 필요한 범위만 사용한다.

## 5. Planning

- 주요 코드 변경 전 현재 구현과 영향 범위를 분석한다.
- 변경할 영역과 구현 방향을 먼저 계획한다.
- 기존 기능에 미치는 영향을 계획 단계에서 확인한다.
- 계획 검토가 필요한 작업은 실제 코드 수정 전에 사용자에게 확인한다.

## 6. Implementation

- 승인된 계획과 요청 범위에 따라 코드를 수정한다.
- 기존 기능과 데이터 구조를 가능한 한 유지한다.
- 불필요하게 복잡한 구현을 추가하지 않는다.
- 유지보수가 쉬운 구조와 명확한 코드를 우선한다.

## 7. Review

코드 변경 후 다음 항목을 검토한다.

- 기존 기능을 깨뜨릴 가능성이 있는 코드
- 중복되거나 불필요한 코드
- 사용되지 않는 코드
- 유지보수가 어려운 구현
- 접근성 또는 반응형 UI 문제
- 요청 범위를 벗어난 변경

발견된 모든 문제를 자동으로 수정하지 않는다.
수정 범위와 영향을 확인한 뒤 필요한 항목만 수정한다.

## 8. Verification

최종 작업 완료 전 다음 항목을 확인한다.

- 최초 요구사항이 모두 반영되었는가?
- 기존 기능이 정상적으로 유지되는가?
- 기존 데이터가 유지되는가?
- 개발 규칙을 준수했는가?
- Review에서 발견된 주요 문제가 해결되었는가?
- 추가 확인이 필요한 사항이 남아 있지 않은가?

## 9. Final Response

작업 완료 후 다음 내용을 간단하게 정리한다.

1. 변경한 파일
2. 주요 변경 내용
3. 수행한 검증
4. 남아 있는 확인 사항
