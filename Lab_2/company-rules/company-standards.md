# Company Development Standards

> **Purpose**  
> 이 문서는 IBM Bob을 사용하는 모든 프로젝트에 공통으로 적용하는 기업 개발 기준 예시입니다.  
> Lab 02에서는 이 파일을 **Global Rule**로 적용합니다.

---

## 1. General Development Rules

- 새로운 코드를 작성하기 전에 기존 구현과 프로젝트 구조를 먼저 확인한다.
- 기존 코드와 공통 모듈을 우선 재사용하고, 불필요한 중복 코드를 만들지 않는다.
- 요청받은 범위를 벗어난 파일이나 기능은 임의로 변경하지 않는다.
- 기존 동작을 변경해야 하는 경우에는 변경 이유와 영향 범위를 먼저 설명한다.
- 작업 완료 후 변경한 파일과 주요 변경 내용을 요약한다.

---

## 2. Change Scope

- 사용자가 요청한 기능과 직접 관련된 코드만 수정한다.
- 대규모 리팩터링은 별도 요청이 없는 한 수행하지 않는다.
- 파일 삭제, 대량 수정, 프로젝트 구조 변경은 실행 전에 사용자 확인을 받는다.
- 기존 기능을 유지할 수 있는 최소 변경 방식을 우선한다.

---

## 3. Security

- Password, API Key, Access Token, Secret 등의 민감정보를 소스코드에 직접 작성하지 않는다.
- 인증, 권한, 보안 설정을 임의로 제거하거나 완화하지 않는다.
- 외부 서비스로 민감한 프로젝트 정보를 전달해야 하는 경우 먼저 사용자에게 알린다.
- 보호 대상 파일이나 환경 설정 파일을 수정해야 하는 경우 실행 전에 승인을 요청한다.

---

## 4. Dependencies and External Tools

- 새로운 Library, Package, Extension을 추가하기 전에 사용자 승인을 요청한다.
- 기존 Dependency로 해결 가능한 경우 새로운 Dependency를 추가하지 않는다.
- 설치 명령이나 시스템 변경 명령을 실행하기 전에 명령과 목적을 설명한다.
- 외부 Tool 또는 MCP Tool을 사용할 때는 필요한 범위의 정보만 전달한다.

---

## 5. Quality and Validation

- 코드 변경 후 기존 기능이 유지되는지 확인한다.
- 프로젝트에 Build, Test, Lint, Type Check 등의 검증 절차가 있으면 가능한 범위에서 실행한다.
- 자동 검증을 통과하더라도 요구사항 충족 여부는 별도로 확인한다.
- 검증에 실패한 경우 원인을 설명한 후 수정 방향을 제시한다.

---

## 6. Human-in-the-Loop

다음 작업은 자동으로 진행하기보다 개발자의 확인을 우선한다.

- 주요 파일의 대규모 변경
- 파일 삭제
- 외부 Dependency 추가
- 시스템 또는 환경 설정 변경
- 보안과 관련된 설정 변경
- 영향 범위가 명확하지 않은 명령 실행

---
